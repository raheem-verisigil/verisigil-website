Engineering discipline · Evidence-led systems
The operational problem

Authorisation is not enough if it is not checked at the moment of consequence.

AI agents increasingly interact with systems that move money, change records, deploy software and trigger business processes. An approval made earlier may no longer describe the action about to execute.

  • ✓Re-evaluate authority and conditions at the declared execution boundary.
  • ✓Bind the decision to the exact action and parameters being executed.
  • ✓Refuse when required conditions cannot be established.
  • ✓Produce a receipt that can be independently checked.

Platform capabilities

A defined control point between AI intent and external effect.

VeriSigil is designed to complement existing identity, policy and application controls—not replace them.

01 / RUNTIME

Runtime Authority

Evaluate whether the specific action remains authorised under the current conditions at the declared boundary.

02 / EXECUTION

Parameter-Locked Execution

Bind the governed decision to the exact action and parameters submitted through the tested execution path.

03 / ENFORCEMENT

Fail-Closed Runtime

Required conditions that cannot be established do not become implicit permission on the governed path.

04 / EVIDENCE

Cryptographic Execution Receipts

Generate evidence of the enforcement result that can be checked independently of the originating runtime.

05 / INTEROPERABILITY

API-First Integration

Evaluate a defined workflow through the documented API. Additional framework adapters are enabled only when validated.

06 / OPERATIONS

Bounded Deployment

Start with a declared workflow and test surface, document assumptions, and expand only when evidence supports it.

How it works

Four steps. One explicit execution boundary.

The control is evaluated against the action that is about to happen—not a generic agent score or a retrospective log.

Establish authority

Identify the current authority and conditions relevant to the declared workflow.

Bind the action

Specify the exact action and parameters that the governed path will execute.

Allow or refuse

Enforce the decision at the declared protected boundary under tested conditions.

Verify the receipt

Inspect the resulting evidence and independently verify its integrity.

Evidence status

Commercial confidence starts with an honest claim boundary.

We distinguish verified evidence, demonstrated behavior, pending confirmation and what is not yet proven.

IMPLEMENTED

Durable receipt adapter

Supabase insert/read/consume code exists in the staging evaluation branch; deployed API round-trip is not yet independently verified.

IMPLEMENTED

Fail-closed authorization

Middleware and synthetic tests cover missing receipts, proposal binding and one-time consumption. Exact full-suite result is pending.

SQL TEST REPORTED

Atomic receipt consumption

A rollback-based SQL smoke test reported first consume succeeds and second returns no record. This is not a two-instance API test.

HISTORICAL

Earlier 11/11 STILL result

Previously reported on an earlier reference build. It is not evidence that the current Terry staging candidate passed live Supabase integration.

NOT PROVEN

Restart and multi-instance recovery

Authority/state registries remain in-memory in the current staging harness; restart recovery and independent-instance concurrency remain open.

NOT PROVEN

Downstream actuator enforcement

A VeriSigil authorization response does not yet prove that an external customer actuator cannot be bypassed.

The Terry test currently uses a synthetic in-memory receipt store. The direct database smoke test is separate from API-level persistence. Production-wide authorization, universal prevention, regulatory certification and legal compliance are not permitted claims. See the current evidence baseline.
